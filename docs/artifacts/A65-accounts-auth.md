## Резюме

- **Один аккаунт HoT**, к нему привязаны 1–N identity: Google (`sub`) и WHOOP (`user_id`). Входить можно любой. Паролей, почтовых кодов и SMS нет.
- **Свои сессии:** access-токен 15 мин (подпись Ed25519) + refresh с ротацией, детектом повторного использования и привязкой к ключу устройства в Android Keystore. «Выйти везде» и список устройств — в «Я › Аккаунт».
- **Сервер хранит минимум:** id аккаунта, identity, хэши refresh, зашифрованный бэкап (ключа у сервера нет), токены WHOOP (как сейчас). Имя, фото, «О себе» и здоровье — только на телефоне и в E2E-бэкапе.
- **Ключ бэкапа без пароля:** Google Block Store + код восстановления (24 символа) как запасной путь. Passkey PRF — этап 2.
- **152-ФЗ:** сейчас (только основатель, вне РФ) ничего не блокирует. Код пишем за интерфейсом `AccountStore`; **до первого тестера из РФ** — перенос хранилища аккаунтов и бэкапов в РФ (Yandex Cloud, ru-central1), Worker остаётся прокси. Проверка юристом обязательна.
- **Срок:** ядро без юриста ≈ 12 дней Агента 5 (≈ 7–8 календарных при параллели), перенос в РФ +3–4 дня.

## 2. Вход и identity

### 2.1 «Войти через Google»

| # | Где | Что |
|---|---|---|
| 1 | телефон → `POST /auth/nonce` | Worker выдаёт `nonce` (подписан HMAC, живёт 5 мин, одноразовый — id в DO) |
| 2 | телефон | Credential Manager: `GetSignInWithGoogleOption` (кнопка) или `GetGoogleIdOption(filterByAuthorizedAccounts=true, autoSelect)` (тихий повторный вход); `serverClientId` = Web client id; `nonce` из шага 1. Скоупы: только `openid` + `profile` (имя, фото), почта на сервер не идёт |
| 3 | телефон → `POST /auth/google {id_token, device_pub, device_sig}` | ID-токен + открытый ключ устройства (§3.3) |
| 4 | Worker | проверка ID-токена: **подпись** (RS256, ключи Google JWKS `googleapis.com/oauth2/v3/certs`, кэш по `Cache-Control`, `kid`); **`iss`** ∈ {`accounts.google.com`, `https://accounts.google.com`}; **`aud`** = наш Web client id; **`exp`** > now (допуск 60 с), `iat` не старше 10 мин; **`nonce`** совпал и погашен. Ключ identity — только `sub`, **никогда email** |
| 5 | Worker | `(google, sub)` есть → вход в этот аккаунт. Нет → экран «У тебя уже есть HoT? Войти через WHOOP» → иначе новый аккаунт (если есть приглашение, §2.5) |
| 6 | ответ | `{access, refresh, account_id, identities[]}` |

Имя и фото телефон берёт из `GoogleIdTokenCredential` (`displayName`, `profilePictureUri`) локально; на сервер они не передаются.

### 2.2 «Войти через WHOOP»

Переиспользуем поток среза 1 без изменений протокола: `POST /whoop/authorize {code_challenge}` → подписанный `state` с PKCE → `POST /whoop/token {code, state, code_verifier}`. Меняется только ответ `/whoop/token`: вместо `hs1.<user_id>…` — сессия аккаунта (§3). В `state` добавляется `intent` (`login` | `link`) и для `link` — хэш `account_id` + `sid`, чтобы код нельзя было привязать к чужому аккаунту (CSRF-привязка). Email из `profile/basic` отбрасывается.

### 2.3 Привязка, отвязка, конфликты

| Ситуация | Правило |
|---|---|
| Привязать новую identity | нужно: живая сессия **и** step-up (вход этой сессии ≤ 10 мин назад или повторный вход текущей identity) **и** свежий вход новой identity (Google с новым `nonce`, WHOOP с `intent=link`) |
| Identity уже привязана к **другому** аккаунту | `409 identity_in_use`. Экран: «Этот Google уже привязан к другому аккаунту HoT». Кнопки: «Войти в тот аккаунт» (выход отсюда с предложением сохранить копию) · «Отмена». Автослияния нет |
| Отвязать identity | только если остаётся ≥ 1. Отвязка WHOOP = `/whoop/disconnect` (отзыв токенов WHOOP, стирание `WhoopVault`): синхронизация WHOOP останавливается |
| Автопривязка по совпадению email | **никогда** (путь к захвату аккаунта) |
| После привязки | пуш и строка в «Аккаунт»: «Привязан Google · 08.11 13:40 · Pixel 9 Pro XL» |
| Смена аккаунта на телефоне | один аккаунт на установку: «Выйти» → предложение бэкапа → локальная база стирается (`DatabaseKeyProvider.destroy`) → вход |

### 2.5 Allowlist

`ALLOWED_WHOOP_USER_IDS` заменяется приглашениями: одноразовый код (хэш в хранилище, срок 14 дней) при создании аккаунта. Без кода новый аккаунт не создаётся (fail closed). Основатель — по миграции (§3.5).

## 3. Сессии

### 3.1 Токены

| | Access | Refresh |
|---|---|---|
| Формат | JWS EdDSA (Ed25519), `kid` для ротации ключа | непрозрачный `hr1.<sid>.<32 случайных байта>` |
| Claims / содержимое | `iss=hot-edge`, `sub=account_id`, `sid`, `iat`, `exp` | — |
| Жизнь | 15 мин | скользящая 30 дней, абсолютная 180 дней → тихий повторный вход (Google auto-select / WHOOP) |
| На сервере | не хранится; маршруты проверяют подпись | `SHA-256(pepper ‖ token)` текущего и предыдущего |
| На телефоне | только в памяти | Tink AEAD на K_field (Keystore), SharedPreferences вне бэкапа — как `EncryptedWhoopCredentialStore` |

### 3.2 Ротация и детект повторного использования

- Каждый `POST /auth/refresh` выдаёт новую пару; старый refresh помечается использованным.
- Повтор **того же** старого refresh в течение 30 с (сетевой ретрай) → тот же ответ (идемпотентно).
- Повтор позже или повтор после ротации → **отзыв всей сессии `sid`** (семейство), пуш «Вход на устройстве прерван из соображений безопасности», событие в аудит.
- Single-flight внутри Durable Object (как обновление WHOOP в `vault.ts`).

### 3.3 Привязка к устройству

- При входе телефон создаёт EC P-256 ключ в Android Keystore (StrongBox, если есть; неэкспортируемый) и отправляет открытую часть.
- `/auth/refresh` несёт подпись `sign(sha256(refresh) ‖ ts ‖ server_nonce)`; без подписи ключом этого устройства refresh бесполезен (украденный файл не работает на другом устройстве).
- Play Integrity — этап 2.

### 3.4 Отзыв

| Действие | Что происходит |
|---|---|
| «Выйти» | `POST /auth/logout` → сессия `sid` отозвана; ключ устройства удалён |
| «Выйти везде» | все `sid` аккаунта отозваны, `session_epoch++`; чувствительные маршруты (привязка, удаление, бэкап) сверяют сессию с хранилищем; остальные — подпись access (окно ≤ 15 мин) |
| Список устройств | модель, дата входа, последняя активность; «Завершить» по строке |
| Ротация ключа подписи | новый `kid`, старый принимается до истечения access (15 мин) |

### 3.5 Миграция с `hs1`

Новая версия приложения при старте: `POST /auth/migrate` с `hs1.<user_id>…` → проверка хэша в `WhoopVault` → создаётся аккаунт с identity WHOOP → выдаётся пара токенов; `hs1` гасится. Через 2 недели маршрут удаляется, `ALLOWED_WHOOP_USER_IDS` — тоже.

## 4. Данные на сервере и бэкап

### 4.1 Хранит / не хранит

| Хранит | Не хранит |
|---|---|
| `accounts` (id, создан, статус, `session_epoch`) | имя, email, фото, год рождения, пол, «О себе» |
| `identities` (provider, subject, привязан, последний вход), уникально `(provider, subject)` | данные о здоровье, метрики, журнал дня, `event_log` |
| `sessions` (sid, account, ключ устройства, хэши refresh, сроки, отзыв) | токены Google (мы их не получаем) |
| `backups` (blob в объектном хранилище, размер, версия, метаданные обёртки ключа; последние 2) | ключ бэкапа |
| `invites` (хэш кода, срок, кем использован) | IP-адреса (только в лимитере, не пишутся) |
| `audit` (событие, время; 90 дней) — вход, привязка, отзыв, удаление | тела запросов (логи — только `{m, s, ms}`) |
| `WhoopVault` — токены WHOOP (как сейчас) | |

### 4.2 E2E-шифрование бэкапа

Ключ бэкапа `K_bk` — 32 случайных байта на телефоне. Бэкап (экспорт базы, аватар, настройки) шифруется Tink StreamingAead `AES256_GCM_HKDF_1MB`, AAD = `account_id ‖ version`. Сервер видит только шифротекст. Вопрос — как вернуть `K_bk` на новый телефон без пароля.

| Вариант | Как | Плюсы | Минусы | Вывод |
|---|---|---|---|---|
| **А. Google Block Store** | `K_bk` в `BlockstoreClient.storeBytes(…, shouldBackupToCloud=true)`; Google переносит его на новый телефон при восстановлении из облачной копии | невидимо для человека; E2E у Google при блокировке экрана (`isEndToEndEncryptionAvailable`); работает и для входа через WHOOP (Block Store привязан к Google-аккаунту устройства, а не к нашему входу) | только Android + Play services; нет при настройке телефона «с нуля» без восстановления; без блокировки экрана — не E2E [проверить на Pixel] | **основной** |
| **Б. Код восстановления** | 128-битный код, 26 символов Crockford base32 (6 групп); KEK = HKDF-SHA256(код) — код высокоэнтропийный, медленный KDF не нужен; на сервере `wrap(K_bk, KEK)` | не зависит от Google и платформы; работает всегда | человек теряет коды; один экран «Сохрани код» | **запасной, обязателен** |
| В. Passkey PRF | `K_bk` обёрнут ключом из расширения WebAuthn `prf` passkey (Google Password Manager синхронизирует E2E) | кросс-платформенно, без кодов | поддержка PRF в Credential Manager и GPM — [проверить Агенту 5]; passkey — этап 2 | **этап 2** |

**Рекомендация: А + Б.** На сервере хранятся до двух обёрток: Block Store обёртки не требует (ключ лежит в Block Store как есть), код — `wrap_code`. Потерял телефон без облачной копии и код → бэкап не восстановить (так и задумано: сервер не может расшифровать). Это прямо пишется на экране кода.

**D-058 и бэкап.** При отзыве S4 телефон сразу выгружает новый бэкап и удаляет старые версии на сервере: в бэкапе не остаётся данных S4, кроме отметки `ed_care_keep`. При восстановлении `ED_CARE` и история скрытия восстанавливаются вместе с базой — безопасность переживает смену телефона.

## 5. Профиль: аватар и «О себе»

### 5.1 Аватар

| Пункт | Решение |
|---|---|
| По умолчанию | вход через Google и есть фото → фото Google (скачано 1 раз на телефон); иначе — знак Титана. A61 «инициал или глиф» сохраняется как вариант |
| Своё фото | Android Photo Picker (без разрешения на хранилище) или камера через `TakePicture` (без разрешения CAMERA) |
| Обработка | обрезка 1:1 с круглой маской, масштаб до 512×512, WebP; **EXIF (GPS, модель) удаляется** |
| Хранение | файл в `filesDir`, Tink StreamingAead на K_field; в E2E-бэкапе. На сервер отдельно не идёт |
| LLM | в MVP **не уходит никогда**; если понадобится — отдельный opt-in `avatar_ai` |
| Биометрия? | **Нет**, пока не распознаём лицо и не используем фото для установления личности (152-ФЗ ст. 11). Любое распознавание лица = новое решение + ревью 7 [проверить юристу] |
| Где виден | только у человека: кружок справа, карточка «Ты». Не в «Титане недели» и не в открытках без явного выбора |

### 5.2 «О себе»

| Пункт | Решение |
|---|---|
| Поле | свободный текст до **500 символов**, подсказка «Что Винсу стоит знать о тебе: работа, ритм, что важно» |
| Класс | **S4**: в тексте могут быть данные о здоровье. SQLCipher + Tink AEAD по полю (A14 §3.1); в E2E-бэкапе |
| Винсу | только с согласием `about_mentor` (выкл. по умолчанию, A62): текст целиком в `ContextPack` текущего разговора. Без согласия не уходит никуда |
| CrisisGuard | при сохранении — локальный словарь `CrisisGuard` (A07, ADR-15). Срабатывание: сохранение не блокируется, один раз показывается карточка помощи (112 · 911, D-057 п. 4), событие `safety.crisis` без текста. `ED_CARE` от текста «О себе» **не включается** (D-057 п. 2: одно слово не запускает) — тексты и порог — Агент 10 |
| Удаление | кнопка «Очистить», и вместе с данными S4 при отзыве `health_self` [уточнить 7: «О себе» ≠ медфлаги, но может их содержать] |

**Агенты 7 и 10 — оценка:** фото без распознавания — обычные ПДн (S2), не биометрия; свободный текст — потенциально данные о здоровье, отсюда S4, opt-in для Винса и CrisisGuard. Нужна проверка текстов подсказки и карточки (10) и формулировки `about_mentor` (7).

## 6. Удаление аккаунта

| Шаг | Что |
|---|---|
| Где | «Я › Аккаунт › Удалить аккаунт» + веб-страница `https://<edge>/account/delete` (Google Play: ссылка без установки приложения) |
| Подтверждение | step-up (повторный вход Google или WHOOP) + экран последствий + «Сначала сохранить копию файлом» (D-019) |
| Сервер, сразу | отзыв всех сессий; `/whoop/disconnect` (отзыв токенов WHOOP, стирание `WhoopVault`); удаление `identities`, `backups` (объекты), `invites`; аккаунт → `deleted` |
| Сервер, ≤ 30 дней | технические копии провайдера; аудит — строка «аккаунт удалён» без идентификаторов |
| Google | токенов нет — отзывать нечего; подсказка «Убрать HoT из сторонних приложений Google» со ссылкой |
| Телефон | полное стирание: `DatabaseKeyProvider.destroy`, ключ устройства, Block Store `deleteBytes`, аватар. Включая `event_log`, `safety.crisis` и `ED_CARE` с `ed_care_keep`: это и есть «удалить всё» из D-058 п. 5 — на сервере этих данных и не было |
| Веб-путь | вход Google (Identity Services, web) или WHOOP (OAuth, https-redirect — зарегистрировать в WHOOP) → то же удаление сервера; телефон при следующем запуске получает `401 account_deleted` и стирает себя |

### 7.2 Где разместить сервер аккаунтов

| Вариант | Как | Плюсы | Минусы |
|---|---|---|---|
| А. Всё в Cloudflare | `AccountVault` (DO, SQLite) + R2 для бэкапов | 0 новой инфраструктуры, быстрее всего, один стек | первичная запись ПДн граждан РФ за рубежом — нарушение ч. 5 ст. 18 для тестеров из РФ; R-07 |
| Б. Аккаунты в РФ, Worker — прокси | Yandex Cloud ru-central1: Cloud Functions + Managed PostgreSQL + Object Storage — `accounts`, `identities`, `sessions`, `backups`, а также `WhoopVault` (токены WHOOP + `user_id` — тоже ПДн). Worker проверяет access, проксирует WHOOP/LLM, ничего не хранит | закрывает ч. 5 ст. 18; запасной путь для R-07; бэкап и так E2E | +3–4 дня; вторая инфраструктура и деплой; оплата Yandex Cloud из США [проверить]; задержка Worker → РФ |

## 9. Угрозы и защита

| Угроза | Защита |
|---|---|
| Подмена или повтор ID-токена Google | подпись JWKS, `aud` = наш client id, `iss`, `exp`, одноразовый серверный `nonce` |
| Перехват кода WHOOP (custom scheme) | PKCE + подписанный `state` (уже в коде) |
| Кража refresh с телефона | Keystore + Tink; привязка к ключу устройства; ротация и детект повторного использования → отзыв семейства |
| Кража access | 15 мин; «выйти везде» + `session_epoch` для чувствительных маршрутов |
| Захват аккаунта через привязку (злоумышленник со свежей сессией привязывает свой Google) | step-up ≤ 10 мин, `state`/`nonce` с `account_id`, пуш о привязке, список identity, «выйти везде» удаляет и сессии, отвязка в 1 тап |
| Автослияние по email | не делаем |
| Утечка БД сервера | refresh — хэши с pepper; бэкапы E2E; токены WHOOP AES-256-GCM; имён и почт нет |
| Перебор приглашений и входа | rate limit (как `/whoop/*`), коды 128 бит |

## Передача
- **Артефакт:** `docs/artifacts/A65-accounts-auth.md` · v0.1 · спецификация к реализации (D-062).
